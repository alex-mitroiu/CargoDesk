Status update — verified 2026-08-25
This plan was never executed. The codebase instead built 3 real extracted microservices along a completely different path — document-distribution (:3002, v0.64.0), pdf-render (:3003, v0.66.0), and contract-management (:3004, v0.68.0, the only one running alongside local tables via an app_settings.contract_source toggle rather than replacing them) — none of which existed yet when this plan was written and none of which it anticipates. No Postgres/DuckDB split happened; the schema is still one SQLite file (plus each service's own). The live schema is 77 tables today, not the 36 this plan's own header states as baseline. The entire "MAEU Epic" below (MAEU-001–004, and SCHED-006 which blocks on it) is dead — the Maersk Developer Portal integration it depends on was removed as obsolete in v0.72.1; treat every MAEU-* story on this page as removed, not pending. booking_offices, admin_events, and schedule_syncs don't exist anywhere in the real schema. Real shipment IDs are SHP- prefixed (e.g. SHP-XXGOJ1), not the SHPMT-XXXXXX convention this document proposes. And SCHED-001's own "Done" claim that shipment_schedules has a hard FK-cascade to shipments is now false — since v0.54.0 that column is nullable, to support ownerless "template" rows from the Schedule Generator.
Motivation
Security isolation
Password hashes, API keys, and JWT secrets live in auth schema with separate DB-level permissions. A shipment data export can never expose credentials.
Concurrent writes
SQLite serialises all writes through a single lock. Multiple operators working simultaneously will hit contention as shipment volume grows.
Event-driven integrations
Inbound adapters (Maersk schedule sync, future PDM user provisioning) need atomic cross-table transactions — write event log + update shipment in one commit.
Migration cost grows
36 tables today. Each new feature adds cross-schema dependencies. A 12–18 day migration now becomes 30+ days in 6 months.

Key technical decisions
Decision Options Recommendation Rationale
Query driver pg (raw SQL) vs Prisma ORM vs Drizzle pg (node-postgres) Keeps the existing hand-written SQL style. No schema generation step. Easier to review each query individually during migration.
Async conversion Adapter shim (fakes sync) vs full per-route async rewrite Per-route async A sync shim using worker threads is fragile. Taking the async debt route-by-route is more work upfront but yields clean, auditable code.
Row IDs Keep custom UIDs (SHPMT-XXXXXX) vs UUID vs BIGSERIAL Keep UIDs No data migration needed. Human-readable in logs and URLs. Can add a BIGSERIAL surrogate key later for internal FK performance if needed.
Schema migrations (ongoing) Manual versioned SQL vs Flyway vs Liquibase vs Prisma Migrate Versioned SQL files Matches the current migration array pattern. No new toolchain dependency. Files committed alongside code, reviewed in PRs.
Local dev Docker Compose vs local PG install vs Neon serverless Docker Compose Reproducible across machines. docker-compose up replaces the current zero-setup SQLite file. Works offline.
Connection pooling pg-pool (app-level) vs PgBouncer (server-level) pg-pool Simpler for a single Express process. PgBouncer adds a separate infrastructure component — revisit only if connection count becomes a bottleneck.
Analytics layer PG materialized views vs DuckDB vs Snowflake DuckDB In-process, no server, reads PG via FDW or nightly sync. Replaces the slow GROUP BY aggregations in the margin/dashboard routes without infrastructure overhead.
Maersk API key scope Single Consumer Key for all 4 APIs vs per-API keys Single key (confirmed) The developer portal shows one Consumer Key covering Commodities, Vessels, Locations, and Ocean Booking Offices. Stored in app_settings — separate from the P2P Schedules key.
Integration adapter pattern — the K+N data hub model

External systems push or are polled by inbound adapters. The hub is the canonical write model. The application never reads directly from external sources — only from the hub's copy. Every inbound update logs an event atomically with the data change.

Open questions — decide before Phase 1
Q1
PostgreSQL hosting target. Local Docker for dev is clear. For production: self-hosted VPS, managed (AWS RDS, Neon, Supabase), or on-premise? This affects connection string config, SSL requirements, and whether PgBouncer is needed.
Q2
DuckDB sync strategy. Does DuckDB read PostgreSQL in real-time via FDW, or is it fed by a nightly ETL job? Real-time FDW is simpler to set up but adds a PG extension dependency. A sync job is more portable.
Q3
Schedule write-back opt-in. When Maersk returns live ETD/ETA that differs from the stored value, should the adapter update automatically or prompt the operator? Automatic is cleaner for the hub model; prompted preserves manual overrides.
Q4
Future identity provider. Is there a corporate PDM or directory (Azure AD, Okta, LDAP) that should provision users into auth.users? Knowing this upfront shapes the user sync adapter design in Phase 2.
Q5
Cutover strategy. Big-bang cutover (all routes switch at once, risky) or rolling per-schema (auth first, then MDM, then ops)? Rolling is safer but requires the dual-driver shim to stay stable for 2–3 weeks.
Q6
Maersk MDM sync frequency. Commodities and vessels are slow-moving MDM — weekly sync is sufficient. Port locations (14,269 rows) change more frequently. Should the Locations adapter run nightly or be manually triggered? WebSocket progress reporting is already in scope.
