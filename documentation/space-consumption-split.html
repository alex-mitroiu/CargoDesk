Design note · Space Configuration

Space Consumption Split

Today one number — consumedTEU — answers "how much space is used?" regardless of whether a carrier ever actually confirmed it. This plan splits it into Confirmed / Pending / Rejected, so the bar shows what's real.

01 — The gap

One bar, three different truths

A shipment counts toward an allocation's consumed TEU the instant it's linked — whether its carrier booking was just auto-Created, sent and awaiting reply, confirmed with different details than requested, flatly rejected, or genuinely confirmed. loadConsumedTeuMap() sums TEU across every linked shipment with zero regard for carrier_bookings.status.

That means a space configuration can show "82% consumed" when most of that is still a carrier maybe saying yes — and a rejected booking keeps occupying space on the bar forever, with nothing to tell an operator it needs re-booking.

02 — New model

Three buckets, one rule each

Bucket assignment is driven entirely by the existing carrier_bookings.status field — the operator's own action, not the carrier's raw EDI reply. Only Confirmed actively deducts.

Booking state Bucket Deducts from available space?
Operator clicked Confirm — status = 'Confirmed' Confirmed Yes — this is the only thing that reduces remainingTEU.
Auto-created, not yet transmitted — status = 'Created' Pending No. Still counted as demand — an existing booking record claims space whether or not it's been sent yet.
Sent to carrier, awaiting reply — status = 'Pending' Pending No.
Carrier confirmed with different details — new outcome, operator hasn't reviewed yet Pending No — stays Pending until the operator reviews the diff and clicks Confirm themselves.
Carrier rejected — status = 'Rejected' Rejected No — but shown as its own visible segment, not folded into Pending.
Booking cancelled — status = 'Cancelled' Excluded No — dropped from the bar entirely, no live demand left.
Shipment linked to allocation, no carrier_bookings row yet Pending No — same reasoning as Created: the shipment already claims the space.
Escalation on Rejected is explicitly out of scope. The user's own framing: a rejected booking needs a real re-booking/escalation workflow that "we need to map out and integrate" — separately. This pass only makes Rejected visible as its own segment; it does not build any escalation mechanics.
03 — New EDI outcome

"Confirmed with Changes"

Today a simulated carrier reply is binary: confirmed or rejected. Real carriers routinely confirm a booking with a different vessel, voyage, or ETD than what was requested — that state doesn't exist anywhere in the schema yet. This adds it as a genuine third outcome, not a flag folded into Pending.

Every field the booking request sends gets a row — column headers, one row per field, as specified. Rows that actually differ are highlighted; everything else reads as confirmation the rest of the request went through untouched.

Confirming a "Confirmed with Changes" booking still only flips carrier_bookings.status to Confirmed — it does not auto-rewrite the shipment's own schedule/legs with the carrier's proposed vessel/voyage. That decoupling is a standing decision in this codebase (v0.35.0) and this feature doesn't reopen it; the operator sees the diff and updates the schedule by hand if they choose to.

05 — Answered questions

Clarifications from this round

QuestionDecision
What triggers the Confirmed deduction?The operator's own Confirm click — not the carrier's raw EDI reply alone.
Does "confirmed with different details" need real modeling?Yes — a genuine third outcome, own state, not folded into Pending.
What does the Review tab need?A new Sent-vs-Received table, one row per field, with column headers.
Does a not-yet-sent (Created) booking count as demand?Yes — any existing booking record counts as Pending, sent or not.
How should Rejected display?Its own visible segment, separate from Pending. Escalation workflow is future work.
06 — Build sequence

Zero schema migrations

Every new concept fits inside columns that already exist — carrier_bookings.status/last_response_status are plain TEXT with no CHECK constraint, and the differing booking details live entirely inside edi_messages.raw_payload, already stored today. Nothing to migrate.

  1. routes/edi.jsThird outcome, end to end

    New simulatedConfirmedWithChangesResponse() helper; extend applyBookingResponse's ternaries to a 3-way switch; extend simulate-response's outcome validation; booking status stays unchanged (still requires the operator's own Confirm) for both confirm variants, same as today's plain "confirmed" reply.

  2. TestToolsPage.jsxSimulator UI

    Third button + conditional Vessel/Voyage/ETD override fields, shown only for the new outcome.

  3. ShipmentCarrierBookingReviewPage.jsxSent vs. Received table

    New component built client-side from data already fetched (outbound vs. latest inbound payload), styled on the existing Equipment-table grid pattern; diff rows highlighted.

  4. routes/allocations.jsSplit loadConsumedTeuMap()

    One query, LEFT JOIN carrier_bookings, bucket by status per the rule table above. Update all three call sites (GET /allocations, PUT /allocations/:id, GET /allocations/match) to return confirmedTEU / pendingTEU / rejectedTEU, and recompute remainingTEU = allocated − confirmed.

  5. 4 frontend surfacesStacked bar + overflow indicator

    Replace each single-fill bar with 3 sibling segments; when Confirmed + Pending + Rejected exceeds allocatedTEU, show a small "over-committed" badge rather than rendering past 100% width.

  6. testsCoverage

    Extend carrier-booking.test.js for the new outcome and the confirm-only-deducts rule; extend allocations-crud.test.js for the 3-way split, the Created-counts-as-pending rule, Cancelled exclusion, and the overflow case.
