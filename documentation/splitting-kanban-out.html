Splitting Kanban Out

MDM and Sanctions were both picked because they're clean today. Kanban isn't — it reaches into shipments and users. This proposal is about a different question: Kanban is a feature expected to go away eventually, and the day that happens should mean deleting one folder, not performing surgery on a shared, live database.

A different test than MDM or Sanctions passed

tickets looks entangled by name — shipment_id, assignee_id, a self-referencing parent_id. But look at what's actually in the schema, not the comments describing it, and a real difference shows up.

What removal looks like, either way

This is the actual argument. Not "is Kanban slower to query today" — it isn't — but "what does the day we retire Integration Board actually involve."

What actually has to change

Real scope, named plainly — this isn't free, it's just cheap now and expensive later.

The move

  • Tables — tickets, ticket_links, test_items, test_case_links, kb_projects, kb_versions, kb_columns move to a new Kanban Service, own SQLite, same shape Contract Management already proved (v0.68.0).
  • routes/kanban.js / routes/testcases.js become thin proxies over callKanbanService(), mirroring callContractService() exactly.
  • TICKET_JOIN (the LEFT JOIN users that resolves assignee_name/assignee_initial) can't join across a service boundary — becomes an explicit batch name-resolve the monolith does before responding, the same pattern already used for carrier_agents' agent-name lookups.
  • Two call sites that write from outside Kanban — the ops-automation sweep (auto-creates tickets on server start) and the notification bell's ticket-alert card (reads overdue/due-soon tickets) — switch from a local query to an API call. The one real new plumbing this split adds; everything else is a lift-and-shift.

Timing

Unlike MDM and Sanctions, this one isn't ordered by risk — it's ordered by how soon Integration Board is actually expected to be retired. If that's not imminent, there's no urgency; the point is having the exit built before it's needed, not rushing it alongside the other two.

Draft for discussion — nothing here is built yet. Companion to "Splitting MDM First" and "Splitting Sanctions Next," reasoned from a different goal: painless removal of a feature expected to be temporary, not today's domain boundaries.
