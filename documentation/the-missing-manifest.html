The Missing Manifest

AES/EEI Export Filing and the Pickup service both sit on the same shipment record — and, apart from one indirect gate, know nothing about each other. This traces exactly what each side has today, what real export-compliance rules require of that relationship, and the 10 fixes that close it.

Scope routes/customs-filing.js · LoadingServicePage.jsx · shipment_services · shipment_loading_plan_lines Epic TKT-6A7J45 Stories 10, logged in Kanban
Finding

Zero functional integration exists between the two subsystems. The only connection is a shared shipment_id and one indirect gate — an export filing can be created and submitted without a Pickup ever being ordered, and its ITN never reaches the document a carrier actually checks.

Confirmed by direct code read of both subsystems' full route files, schemas, UI pages, and every cross-table reference in the repo — not inferred.

Why the link matters

This isn't a nice-to-have wiring gap — AES/EEI is a real regulatory filing (15 CFR Part 30, US Census Bureau Foreign Trade Regulations), and its rules are built around the physical movement of cargo, which is exactly what the Pickup service tracks.

01

A filed AES/EEI declaration generates an ITN (Internal Transaction Number), and a carrier is required to have a valid one on the export manifest before it will load the cargo. A shipment can be turned away at the port without it.

02

Filing deadlines are set relative to actual vessel loading, not to when someone happens to click Submit in the app — which means the filing's timing is genuinely coupled to when cargo is picked up and gated in, not just to when a contract or schedule exists.

03

EEI requires per-line commodity data — Schedule B/HTS number, quantity, weight, value — and the USPPI (U.S. Principal Party in Interest) and Ultimate Consignee. A "some package somewhere is priced" gate isn't the same thing as a filing that actually carries that data.

Current state

verified by direct code read
What each side actually has
  • customs_filings: id, type, status, filing_reference, confirmation_number, rejection_reason, timestamps — nothing else.
  • Filing lifecycle: Draft → Filed → Accepted / Rejected → Draft (reset), fully simulated via Test Tools, no live gov EDI.
  • Filing gate: a Customs Broker party assigned, plus one priced container_packages row anywhere on the shipment.
  • shipment_services (Pickup row): status, vendor, office, requested/confirmed/completed dates.
  • shipment_loading_plan_lines: per-container planned date, sequence, notes — feeds the PU01 document.
  • Pickup's own Routing card already resolves Merchant's vs. Carrier's Haulage from the real leg data.
What never connects
  • The AES/EEI submit payload carries only {filingType, filingReference, pol, pod, note} — no carrier, vessel, voyage, or export date.
  • cargoReadyDate exists on the shipment and feeds the carrier booking-request payload, but is read nowhere in customs-filing code.
  • container_events (Gate In, Loaded, Sailed…) is referenced nowhere in either the filing routes or the Pickup/Loading service code.
  • The customs_cleared milestone exists but is never auto-completed by anything, Accepted filings included.
  • The ITN (confirmation_number) appears in zero other files — not the Bill of Lading builder, not the booking-request payload.
  • Pickup sits under "Export Services" in the sidebar; Customs Filing sits under "Booking & Routing" — different groups, no cross-link.
The one indirect link: the filing-creation gate checks for a priced container_packages row — that's Cargo/Epic 2 data, not Pickup data. It's the only place customs-filing code reaches outside its own table.

The 10 fixes

ordered: compliance risk → data completeness → workflow

Logged as Epic TKT-6A7J45 with one Story per item below, in this same priority order.

1

Propagate the ITN to the Bill of Lading and booking-request payload

Compliance risk

The single most serious gap. An Accepted filing's ITN is generated and then goes nowhere — not onto BL01/MB01, not into the carrier booking-request payload. Add it as an additive detail row on both, populated only once AES_EEI status is Accepted, same pattern the Master B/L's NVOCC row already uses.

TKT-US6LV7
2

Warn on Submit if Pickup hasn't been ordered or confirmed yet

Compliance risk

A filing can be Submitted today with no Pickup service on the shipment at all. Real AES timing is tied to actual cargo movement — add a soft warning (not a hard block, matching this app's existing credit-limit-style philosophy) when Pickup is missing or still Requested.

TKT-JOYVCD
3

Add carrier, vessel, voyage, and export date to the submit payload

Data completeness

Today's payload is just pol/pod/reference/note. Pull conveyance information and export date from the shipment's own SEA leg — the same resolution the booking-request payload already performs — so the transmitted filing actually matches what's shipping.

TKT-WUFH7Y
4

Snapshot per-line commodity, HS code, and value at filing time

Data completeness

The filing has zero commodity columns of its own today — the gate only checks that some package somewhere is priced. Snapshot the actual priced container_packages list (HS code, qty, weight, value) onto the filing at Submit, mirroring the write-time-snapshot idiom already used for contract rates.

TKT-9MVPZP
5

Flag a Filed filing as stale when Pickup, carrier, or cargo changes

Data completeness

Once story 4's snapshot exists, compare it against the shipment's live data and surface a mismatch badge — reusing the exact badge-vs-modal split pattern ContractMismatchModal and PendingRevalidationModal already established — prompting an amend rather than letting a stale filing sit silently Accepted.

TKT-6FMU34
6

Wire an Accepted AES/EEI response to the customs_cleared milestone

Data completeness

The milestone step already exists in the schema — it's simply never completed by anything. One autoCompleteMilestone(shipmentId, 'customs_cleared', …) call in the simulate-response handler, identical to how booking_confirmed/cargo_gated_in/si_submitted already work.

Correction, caught during implementation: this proposed mechanism was wrong — customs_cleared sits AFTER vessel_arrived in the milestone sequence — it's the import/destination-side clearance step, not an export-side one. An Accepted AES/EEI (export) filing was the wrong trigger; ISF/AMS (the import filing) Accepted was wired instead.
TKT-8E858J
7

Check USPPI and Ultimate Consignee completeness in the gate

Data completeness

The gate checks for a broker and a priced line — never that Shipper (USPPI) and Consignee (Ultimate Consignee) data is actually filled in, despite both being legally required EEI fields the shipment already carries. Add a third checklist item to the existing two-item gate.

TKT-GKXJ11
8

Show Pickup status directly on the AES/EEI filing card

Workflow

A one-line, read-only cross-reference — "Pickup: Confirmed for Aug 20" — on the Customs Filing Details page, so an operator isn't tab-hopping between two sidebar groups to answer "is this shipment physically ready to file."

TKT-33GVIF
9

Close the sidebar gap between Pickup and Customs Filing

Workflow

Relocate Pickup (Export side only, so Import's Delivery stays untouched) into Booking & Routing next to Customs Filing, or add a direct "View Pickup Service →" link from story 8's card — either closes a navigation gap between two pages that are functionally adjacent but currently live apart.

TKT-7HRYOB
10

Show a pre-departure filing deadline once a schedule exists

Workflow

The filing page has zero time-awareness today. Once shipments.etd is set, show a simple "Xh until filing deadline" / "Filing overdue" indicator against a configurable offset — the exact regulatory deadline varies by mode and filer type, so a hardcoded precise rule is out of scope here.
