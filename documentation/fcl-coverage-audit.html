01

Methodology

Pulled the FCL/ocean-freight-relevant subset of DocShipper's glossary (docshipper.com/glossary and its curated /logistics-glossary index) — booking, equipment, documentation, customs/regulatory, ports & terminals, and freight charges. Each term was checked against CargoDesk's actual schema and route code directly (grep & read, not assumed).

Scoped to FCL only, per the standing FCL-first sequencing decision — LCL/consolidation is confirmed already logged and deliberately deferred, not re-litigated here.

This is CargoDesk's second gap-analysis pass. The first (v0.69.0) was competitor-driven — it compared CargoDesk against CargoWise, Magaya, Descartes and others, and shipped Freight Audit & Payment plus multi-list denied-party screening off the back of it. This pass asks a different question — not "what do other platforms have," but "does CargoDesk's own model match the industry's own definitions and paper trail" — and surfaces a different, more document-shaped set of gaps as a result.

02

Where CargoDesk already matches the standard

Checked against the glossary's own wording. This list is worth reading before the gaps below — the FCL core is in genuinely good shape.

✓
Demurrage vs. Detention "Demurrage applies when a container remains at the terminal beyond free time… Detention applies when you've taken the container outside the terminal but haven't returned it." — DocShipper
Textbook match, independently computed per container: origin demurrage runs Gate In→Sailed, origin detention runs Empty Pickup→Gate In; destination mirrors it (Discharged→Gate Out demurrage, Gate Out→Empty Return detention). Four independent live-state windows, not two.
✓
VGM (Verified Gross Mass) SOLAS-mandated container weight verification before loading.
Weight, status, and cutoff tracked per container, with its own compliance badge state.
✓
B/L Release Types Original / Telex Release / Surrendered / Seaway Bill — matches the glossary's own definitions almost word for word.
Shipped this session — drives the new "No. of Originals" line on the generated Bill of Lading.
✓
TEU / FEU container types 20ft / 40ft standard sizes, plus reefer, open-top, flat-rack, tank.
Modeled at the container level (DC/HC/RF/OT/FR/TK), with a full pack-item tree underneath for pallets, cartons, and mixed cargo.
✓
THC & accessorial charges
No fixed THC/BAF/CAF field set — instead a generic charge-code registry on cost lines, flexible enough to capture any accessorial a carrier bills, including automated per-container fees.
✓
Booking lifecycle
Real, simulated EDI booking-request flow: Created→Pending→Confirmed/Rejected, with full archived history when a carrier change supersedes a live booking.
✓
EEI/AES & ISF/AMS filing "Electronic Entry Information… advance cargo information requirement." — DocShipper
Simulated but structurally faithful export (AES/EEI) and import (ISF/AMS) filing lifecycle, with Customs Broker role assignment feeding it directly.
✓
IMDG / Dangerous Goods
Class and declaration tracked from the container down to the individual pack item — a single DG pallet in an otherwise clean container doesn't force the whole box to be flagged.
✓
HS Code
Tracked at both container and per-pack-item level, with a per-item override of the container's own default.
✓
Notify Party
Both the fixed shipment role and an extensible "Also Notify Party" additional role.
✓
Live vessel tracking (AIS)
Genuinely ahead of the glossary's own baseline — a persistent AIS feed auto-confirms ETD/ETA from real position reports, something a definitions glossary wouldn't even describe as standard practice yet.
03

Gaps

Six real gaps, each read through two lenses: what it costs the business/user if left unbuilt (PM), and how it would actually land in CargoDesk's existing patterns (Architect).

Master B/L vs. House B/L

Now✓ Closed v0.71.0

"A Master B/L is issued by the ocean carrier to the freight forwarder. The forwarder then issues House B/Ls to individual shippers." — DocShipper

CargoDesk's own most likely operator persona is the forwarder/NVOCC — issuing paper to their own customer while holding different paper from the ocean carrier. shipments.bl_number is one field; it can't hold both.

Additive only: keep bl_number as the House B/L (avoids touching every existing reader), add one nullable master_bl_number column, and one conditional row on the BL01 document builder — same pattern as the Booking Ref row already there.

Correction to the v0.69.0 analysis: that pass bucketed Master/House B/L together with "LCL/consolidation" as one deferred item. That conflates two different things — an FCL container booked through an NVOCC gets a Master and House B/L with zero consolidation involved. The LCL half stays correctly deferred; the Master/House split itself is pure-FCL scope.

Equipment condition at gate in/out (EIR)

Next✓ Closed — container_events.condition_notes/damage_flag

Standard terminal/drayage practice: container condition (damage, cleanliness) is recorded and photographed at every gate movement, signed by trucker and terminal.

A disputed detention charge almost always comes down to proving condition at a specific gate movement. CargoDesk's own D&D pre-audit is otherwise excellent, but has no evidence to point to when a carrier's invoice is contested.

container_events already logs when; extend with nullable condition_notes / damage_flag, and reuse the existing document-upload mechanism for photos (it already carries container_id). Wires into ContainerEventsPanel.jsx's existing log-event form — no new subsystem.

Arrival Notice & Delivery Order documents

Now✓ Closed — AN01/DO01 documents

Arrival Notice: carrier/forwarder → notify party, "your container arrives on X, free time starts." Delivery Order: cargo-release authorization to the destination trucker once the B/L is surrendered.

Two of the highest-frequency documents on any import file — every single shipment touches both. Today a user has to hand-build one via the free-text "Other" doc type, with none of the right fields auto-populated the way BL01/CI01 already are.

Two new DOC_TYPES entries + two builder functions, following the existing buildXHtml pattern exactly. Arrival Notice reads eta/podName/notifyName + the container's own dest_free_time_days (already computed) to state the real free-time deadline. Delivery Order reads the Trucker (On-carriage) party and B/L release status (both already exist). Zero new backend routes — the document-generate endpoint already does everything needed.

Duty / tariff / landed-cost estimate

Later✓ Closed — duty_rate_chapters

Ad Valorem Duty, Duty Drawback, Customs Duty — the actual dollar cost of importing, beyond freight.

"True landed cost" (freight + duty + fees) is one of the most-requested capabilities in any shipper-facing tool — and CargoDesk already tracks both inputs an estimate needs (declared_value, hs_code).

The genuinely hard gap on this list — an accurate duty estimate needs a real, versioned, per-country HS-tariff data source, the same "needs a data business, not code" caveat already applied to carrier networks in the v0.69.0 pass. Realistic first step: a manually-seeded flat-rate-by-HS-chapter estimator, explicitly a ballpark tool, not a broker system of record.

Chassis / drayage equipment

Later✓ Closed — container_events.chassis_provider

Chassis: the wheeled equipment a container rides on for the trucking leg — chassis shortage/pool fees are their own real cost and delay driver.

movement_by already captures Truck/Rail/Barge/Vessel as a mode, but nothing models the chassis itself. Matters a lot for US import-heavy drayage, much less elsewhere — correctly a narrower, later item.

Piggybacks on the EIR extension above rather than needing its own subsystem — a chassis-provider field plus a per-diem charge code is additive once gate-event condition capture exists.

Letter of Credit / documentary compliance

Not recommended

Financial instrument guaranteeing payment, with strict document-compliance requirements against the LC's own exact wording.

Real for trade-finance-heavy shippers, but this is fundamentally a banking workflow that CargoDesk's own documents would need to comply with — not a freight-forwarding workflow. Flagged for completeness, correctly out of the app's core lane.

No architecture note — not recommended for build.
