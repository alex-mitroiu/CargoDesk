When it runs

Once, the first time either Accounting tab is opened on a shipment — not a live sync. Deleting a defaulted line afterward doesn't bring it back.

After it's added

A defaulted line is a normal cost line from that point on — fully editable, deletable, actualizable, postable. The badge is just provenance.

Data model — two new tables

Setups and their lines are separate tables (1→N), matching the existing contracts/contract_legs shape rather than inventing a new pattern. Location fields are plain text against existing MDM tables, not a new lookup structure — countries.region_code already gives every country its region, and port_locations.country_code already gives every port its country, so Region/Country/ Location resolution is a lookup, not new reference data.

CREATE TABLE charge_default_setups (
  id                TEXT PRIMARY KEY,
  principal_id      TEXT DEFAULT '',   -- blank = all principals
  principal_name    TEXT DEFAULT '',   -- denormalized for the list page
  movement_type     TEXT DEFAULT '',   -- 'FCL' | 'LCL' | '' (blank = any)
  location_global   BOOLEAN NOT NULL DEFAULT FALSE,
  origin_region     TEXT DEFAULT '',   -- regions.code
  origin_country    TEXT DEFAULT '',   -- countries.iso2
  origin_location   TEXT DEFAULT '',   -- port_locations.unlocode
  dest_region       TEXT DEFAULT '',
  dest_country      TEXT DEFAULT '',
  dest_location     TEXT DEFAULT '',
  is_active         BOOLEAN NOT NULL DEFAULT TRUE,
  created_at        TEXT NOT NULL,
  created_by        TEXT DEFAULT '',
  updated_at        TEXT DEFAULT NULL,
  updated_by        TEXT DEFAULT ''
)

CREATE TABLE charge_default_lines (
  id           TEXT PRIMARY KEY,
  setup_id     TEXT NOT NULL REFERENCES charge_default_setups(id) ON DELETE CASCADE,
  type         TEXT NOT NULL,   -- 'BUY' | 'SELL'
  charge_code  TEXT NOT NULL,
  description  TEXT DEFAULT '',
  currency     TEXT NOT NULL DEFAULT 'USD',
  amount       REAL NOT NULL DEFAULT 0,
  sort_order   INTEGER DEFAULT 0
)

-- One row per shipment the instant it's first resolved (whether or not a setup actually
-- matched) — the "apply once, never re-sync" rule from the mockup lives here, not in code
-- that has to remember to check it.
CREATE TABLE shipment_charge_defaults_applied (
  shipment_id TEXT NOT NULL REFERENCES shipments(id) ON DELETE CASCADE,
  setup_id    TEXT REFERENCES charge_default_setups(id) ON DELETE SET NULL, -- NULL = no setup matched
  applied_at  TEXT NOT NULL,
  PRIMARY KEY (shipment_id)
)

Matching & precedence algorithm

Runs server-side, once per shipment, the first time GET /api/shipments/:id/cost-lines is called — the one endpoint both the Costs (Buy) and Invoice/Cost Entry (Sell) pages already fetch from on mount, so no frontend change is needed to trigger it.

async function applyChargeDefaults(shipmentId) {
  const already = await query("SELECT 1 FROM shipment_charge_defaults_applied WHERE shipment_id=$1", [shipmentId]);
  if (already.length) return; // already resolved — never re-runs, even if the matching setup changes later

  const shipment = await getShipment(shipmentId);
  const [originCountry, originRegion] = await resolveCountryAndRegion(shipment.pol);
  const [destCountry,   destRegion]   = await resolveCountryAndRegion(shipment.pod);

  const candidates = (await query("SELECT * FROM charge_default_setups WHERE is_active=TRUE"))
    .filter(s => (!s.principal_id || s.principal_id === shipment.principal_id)
              && (!s.movement_type || s.movement_type === shipment.movement_type)
              && (s.location_global || sideMatches(s, 'origin', shipment.pol, originCountry, originRegion))
              && (s.location_global || sideMatches(s, 'dest',   shipment.pod, destCountry,   destRegion)));

  const specificity = s => (s.principal_id ? 1 : 0) + (!s.location_global ? 1 : 0) + (s.movement_type ? 1 : 0);
  candidates.sort((a, b) => specificity(b) - specificity(a) || b.updated_at.localeCompare(a.updated_at));
  const winner = candidates[0] || null;

  if (winner) {
    const existingCodes = new Set((await query("SELECT charge_code FROM shipment_cost_lines WHERE shipment_id=$1", [shipmentId])).map(r => r.charge_code));
    const lines = await query("SELECT * FROM charge_default_lines WHERE setup_id=$1 ORDER BY sort_order", [winner.id]);
    for (const l of lines) {
      if (existingCodes.has(l.charge_code)) continue; // contract or manual line already covers it — never duplicated
      await insertCostLine(shipmentId, { ...l, source: 'principal_default', sourceSetupId: winner.id });
    }
  }
  await query("INSERT INTO shipment_charge_defaults_applied (shipment_id, setup_id, applied_at) VALUES ($1,$2,$3)",
    [shipmentId, winner?.id ?? null, new Date().toISOString()]);
}

sideMatches checks location fields most-specific-first: exact *_location match, else *_country match, else *_region match — exactly one of the three is ever set per side, so this is a single if/else-if chain, not a scoring problem.

Validation rules

  • 01At least one line. Save is rejected if both the Charges and Costs groups are empty — an empty setup can't be created.
  • 02Exactly one location field per side. Unless Global is on, Origin needs exactly one of Region/Country/Location filled, and so does Destination — enforced live in the UI (filling one clears its siblings) and re-checked server-side on save.
  • 03Global disables, not just hides. When the toggle is on, all six location columns are cleared server-side on save, regardless of what the (disabled) inputs show client-side.
  • 04Blank Principal needs confirmation. The save endpoint itself doesn't gate this — it's a client-side confirmation step only, same trust level as any other "are you sure" in the app.
  • 05Charge code must exist. charge_code_definitions turned out to be a different thing entirely (an unrelated auto-injected-SELL-line registry) — the real vocabulary every cost line actually draws from is the fixed 8-code list CostLineForm's own dropdown already uses (Ocean Freight, Origin THC, Destination THC, B/L Fee, Customs, Inland, Haulage, Other). Every setup line is validated against that same list, not a separate one.

API surface

Method & pathPurpose
GET /api/charge-default-setupsList, for the admin page. Includes each line's count for the table's Lines column.
POST /api/charge-default-setupsCreate, with its lines in one payload (setup + lines array). Both scope and lines are validated before any row is written, so a bad request never creates a partial setup — sequential inserts after that, same no-formal-transaction pattern Contracts already uses for its own contract+legs+rates create.
PUT /api/charge-default-setups/:idUpdate scope and replace its lines wholesale (delete-then-reinsert) — simpler and safer than diffing individual line edits for a config this small.
PATCH /api/charge-default-setups/:id/activeActivate/deactivate without touching scope or lines — the list page's own Activate/Deactivate action.
DELETE /api/charge-default-setups/:idDeletes the setup and its lines (cascade). Does not touch any cost line already applied to a shipment — those are real financial records now, independent of the setup that created them.
GET /api/shipments/:id/cost-linesExisting route — gains one line at the top of its handler: await applyChargeDefaults(req.params.id), before the existing SELECT.

Permissions

Managing setups is gated the same way Contracts already are — admin, operator and trade_manager roles (this codebase's real write role set for MDM configs, one wider than this spec first assumed), via the existing requireRole middleware / the frontend's own canManageConfigs. No new role is introduced.
